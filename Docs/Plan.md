# 계획서

## 0. 개요

조이스틱 입력을 CAN 메시지로 변환해 전송하는 조종기 노드와, 이를 수신해 모터를 구동하되 자체 판단으로 명령을 거부할 수 있는 차량 노드로 구성된 2노드 분산 제어 시스템을 설계한다.  두 개의 노드로 분리하고 CAN을 도입한 이유는, 실제 차량 E/E 아키텍처의 최소 단위를 재현하기 위해서이다. 오늘날 차량에서 스티어링 조작은 배선으로 바퀴에 전달되지 않는다. 메시지로 변환되어 네트워크를 타고 흐르고, 수신측 ECU가 이를 해석해 액추에이터를 움직인다. 이 구조에서는 "명령이 도착하지 않았을 때 어떻게 행동할 것인가"가 기능 구현만큼 중요해진다.이 프로젝트의 목표는 동작하는 RC카를 만드는 것이 아니라, 그 질문에 대한 답을 설계로 구현하고 수치로 증명하는 것이다.

### 사용 보드

| 역할 | 보드 |
| --- | --- |
| Node 1: 조종기 | STM32 NUCLEO-L432KC |
| Node 2: 차량 | STM32 NUCLEO-F446RE |

## 1. 시스템 아키텍처

```
┌───────────────────────────────────┐        ┌───────────────────────────────────┐
│  Node 1 : REMOTE (CAN ID 0x100)   │        │  Node 2 : VEHICLE (CAN ID 0x200)  │
│  ── NUCLEO-L432KC (Cortex-M4F) ── │        │  ── NUCLEO-F446RE (Cortex-M4F) ── │
│                                   │        │                                   │
│  CLK : MSI 48MHz (LSE 트리밍)      │  CAN   │  CLK : HSE 8MHz Bypass → 160MHz   │
│  Joystick  ─ ADC1 + DMA           │◄──────►│  HC-SR04 ─ TIM Input Capture      │
│  Buttons×3 ─ EXTI                 │500kbps │  L298N   ─ TIM3 PWM 20kHz         │
│   LCD      ─ I2C1 + DMA           │ 120Ω×2 │  Motor L / R (Differential Drive) │
│  전원 : USB 보조배터리 (배터리 구동) │        │  전원 : 18650 ×2 + 보조배터리      │
└───────────────────────────────────┘        └───────────────────────────────────┘
```

이 시스템의 출발점은 조종기와 차량을 두 개의 독립 컴퓨터로 만든다는 결정이다. 각 MCU는 서로 다른 일을 하며 CAN 버스를 통해 메시지로 통신한다. 노드 1은 사람의 의도를 읽어 메시지로 만들고 노드 2는 메시지를 물리적인 힘으로 구현한다.

Node 1은 계산량이 거의 없기 때문에 NUCLEO-L432KC 보드를 사용하기로 하였고, Node 2는 초음파 센서 반사파 도달 시간 실시간 측정, 두 모터의 PWM을 20kHz로 제어, 동시에 CAN 수신과 안전 상태 판정 체크 등 실시간 부담이 크기 때문에 NUCLEO-F446RE 보드를 사용하기로 하였다.

CAN에는 별도의 클럭 선이 없기 때문에 송신측과 수신측이 각자의 클럭으로 비트 경계를 판단하고 데이터 자체의 엣지를 보며 조금씩 서로 보정해야 한다.

## 2. **Fail-safe 설계**

### 2-1. **단일 소유권(Single Ownership) + 상태 머신**

```
[SensorTask]  ─┐
[CanRxTask]   ─┼─► (Shared State + Mutex) ─► [SafetyTask] ─► g_system_state
[Button/EXTI] ─┘                                                    │
                                                                    ▼
                                                  [MotorTask] ──► PWM (유일한 쓰기 주체)
```

다른 태스크들은 모터를 건드리는 대신, SafetyTask에 데이터를 전송한다. 즉, 판단은 하지 않고 관측만 하는 것이다. 판단은 SafetyTask에서 받은 데이터들을 취합하여 시스템이 어떤 상태여야하는지 결정한다. MotorTask는 20ms마다 깨어나 상태를 읽고, 그 상태에 적합한 출력을 PWM에 쓴다. 이를 통해 SensorTask와 MotorTask의 경쟁 상태가 발생할 수 없도록 한다.

시스템의 상태는 아래와 같이 설계하였다.

| 상태 | 진입 조건 | 모터 출력 | 탈출 조건 |
| --- | --- | --- | --- |
| `INIT` | 부팅 | 정지 | 자가진단 통과 |
| `SAFE_STOP` | 시동 전 / 리셋 후 | 정지 | 조이스틱 중립 버튼
 + Arm 버튼 |
| `RUN` | 정상 | CAN 명령대로 | 아래 조건 발생 시 전이 |
| `EMERGENCY_BRAKE` | 전방 < 15cm AND 전진 명령 | 강제 정지 (후진 허용) | 거리 > 25cm 
(히스테리시스) |
| `LINK_LOST` | 마지막 유효 CAN 수신 후 > 150ms | 정지 | 유효 프레임 3연속 수신 |
| `FAULT` | 센서 무응답 / Bus-Off /
CRC 연속 오류 | 정지 (Latched) | 수동 리셋 |

충돌 위험 감지 거리와 해제 거리가 서로 다른 이유는, 같은 거리(15cm)로 평가를 하게 되면 차량이 15cm 경계에 있을 때 센서 노이즈가 14.9와 15.1 사이로 튀며 모터가 돌았다 멈췄다를 반복하기 때문이다.

### 2-2. **Link Loss Detection**

이 시스템은 네트워크를 사용해 통신한다. 네트워크가 가져오는 위험은 다음과 같다.

1. 메시지가 안옴
    
    조종기가 죽었거나 케이블이 빠진 경우다. 이 때 차량이 이전 명령을 유지하면 마지막 명령이 전진이었을 경우 차는 계속 달린다. 따라서 150ms 타임아웃을 설정하여 정지시킬 것이다.
    
2. 메시지가 오는데 내용이 안바뀜
    
    송신 태스크가 행에 걸렸는데 하드웨어 버퍼가 같은 프레임을 계속 재전송하는 경우다. 이 때는 타임아웃이 아닌 롤링 카운터로 판별해야 한다.
    
3. 메시지가 깨짐
    
    모터 노이즈나 비트 오류로 데이터가 변형된 경우다. 스로틀 0이 100으로 바뀌면 치명적일 수 있다. CRC-8로 검증하고 틀리다면 그 프레임을 버리는 방식으로 방어할 것이다.
    
4. 물리계층이 망가짐
    
    CAN 컨트롤러는 오류가 누적되면 스스로 버스에서 이탈한다(Bus-Off). 이를 감지해 카운터에 기록해두고 재초기화를 시도하는 로직을 추가한다. 핵심은 침묵이 아닌 기록 남기기다.
    
5. 소프트웨어가 멈춤
    
    태스크가 데드락에 빠지면 모든 로직이 무력화된다. 이를 방지하기 위해 독립 워치독이 100ms마다 갱신을 요구하고 갱신되지 않으면 MCU를 강제로 리셋한다. 갱신 책임은 MotorTask가 갖는다. 실제로 액추에이터를 제어하는 태스크가 살아있는지 확인하고싶은 것이기 때문이다.
    

리셋되면 부팅 후 SAFE_STOP으로 들어간다. 이 때 모터는 정지상태이므로, 결과적으로 모든 실패 경로가 정지로 수렴하도록 설계하였다.

| 기법 | 구현 | 검출 대상 |
| --- | --- | --- |
| **Timeout (E2E)** | 20ms 주기 송신 → 150ms 미수신 시 LINK_LOST | 케이블 단선, 조종기 전원 차단 |
| **Rolling Counter** | 0~15 순환, 값이 정지하면 Freeze 판정 | 송신 태스크 행(Hang), 버퍼 재전송 |
| **CRC-8 (SAE J1850)** | Payload 7바이트 → CRC 1바이트 | 비트 오류, 타 노드 오염 |
| **Bus-Off 복구** | HAL_CAN_ERROR_BOF 감지
 → 카운트 기록 후 재초기화 | 물리 계층 이상 |
| **IWDG** | 100ms 타임아웃, MotorTask에서만 갱신 | 태스크 데드락 |

## 3. **클럭 및 CAN 설계**

### 3-1. **조종기(L432KC) 클럭**

CAN은 정확한 클럭을 요구한다. 그러나 NUCLEO-L432KC에는 HSE 크리스털이 실장되어 있지 않다. 고려해볼 수 있는 선택지는 아래와 같았다.

| 방안 | 정확도 | 문제점 | 판정 |
| --- | --- | --- | --- |
| **A. HSI16 그대로** | ±1% 이상 | CAN 허용 오차 초과. 처음엔 되는 듯하다가 **간헐적으로 Error Frame 폭주** | ❌ 불가 |
| **B. SB17 납땜 → ST-LINK MCO 8MHz를 HSE로** | 양호 | **USB를 뽑으면 ST-LINK가 꺼져서 클럭이 사라짐.** 조종기를 배터리로 못 씀. SMD 납땜 필요 | ⚠️ 차선 |
| **C. MSI 48MHz + LSE 32.768kHz 자동 트리밍** | **±0.25% 이내** | LSE 사용 시 D7/D8(PC14/PC15) 사용 불가 (어차피 안 씀) | ✅ **채택** |

STM32L4의 MSI는 LSE 크리스털에 의해 하드웨어적으로 자동 보정(MSI PLL Mode)되며, 이때 정확도가 ±0.25% 이내로 들어온다. NUCLEO-L432KC에는 32.768kHz LSE 크리스털이 기본 실장되어 있으므로 추가 부품 없이 가능하다.

### 3-2. **차량(F446RE) 클럭**

F446RE는 Nucleo-64라 ST-LINK MCO 8MHz가 기본 연결되어 있다(HSE Bypass).

- HSE 8 MHz Bypass → PLL → SYSCLK 160 MHz
- APB1 Prescaler = /4 → PCLK1 = 40 MHz (F446 APB1 최대 45MHz 이내)

PCLK1을 40MHz로 맞추면 아래처럼 두 노드의 tq 개수와 샘플포인트가 완전히 동일해진다. 서로 다른 MCU 간 CAN에서 타이밍 불일치는 가장 흔한 실패 원인이므로, 클럭을 조금 낮추더라도 맞추는 쪽이 이득일 것으로 예상했다.

### 3-3. **CAN 비트 타이밍 (500kbps, 양 노드 동일)**

| 항목 | Node 1 (L432KC) | Node 2 (F446RE) |
| --- | --- | --- |
| 클럭 소스 | MSI 48MHz (LSE 트리밍) | HSE 8MHz Bypass → PLL |
| SYSCLK | 48 MHz | 160 MHz |
| **PCLK1 (CAN 클럭)** | **48 MHz** | **40 MHz** |
| **Prescaler** | **6** | **5** |
| tq 클럭 | 8 MHz | 8 MHz |
| SYNC_SEG | 1 tq | 1 tq |
| **BS1 (TSEG1)** | **13 tq** | **13 tq** |
| **BS2 (TSEG2)** | **2 tq** | **2 tq** |
| **총 tq** | **16** | **16** |
| **Bitrate** | **500 kbps**  | **500 kbps**  |
| **Sample Point** | **87.5%** | **87.5%** |
| **SJW** | **2 tq** | **2 tq** |
- 검산
    - 48 MHz ÷ 6 = 8 MHz, 8 MHz ÷ 16 tq = 500 kHz
    - 40 MHz ÷ 5 = 8 MHz, 8 MHz ÷ 16 tq = 500 kHz

CAN 오실레이터 허용오차는 대략 df ≤ SJW / (20 × NBT_tq) 이다. SJW=1이면 1/(20×16) = 0.3125% 로, MSI의 ±0.25%와 여유가 거의 없다. SJW=2로 올리면 0.625%가 되어 안전 마진이 2배가 되므로 SJW를 2로 설정하였다. 

### 3-4. **CAN 메시지 정의**

**`0x100` — REMOTE_CMD (조종기 → 차량, 20 ms 주기)**

| Byte | 필드 | 타입 | 범위 | 설명 |
| --- | --- | --- | --- | --- |
| 0 | `throttle` | int8 | -100 ~ +100 | 전후진 (%) |
| 1 | `steering` | int8 | -100 ~ +100 | 좌우 조향 (%) |
| 2 | `mode` | uint8 | 0~2 | 0=SAFE, 1=NORMAL, 2=SPORT |
| 3 | `flags` | bitfield | - | bit0=E-Stop, bit1=Arm, bit2=Reserved |
| 4~5 | `reserved` | - | - | 확장용 (0 채움) |
| 6 | `counter` | uint8 | 0~15 | Rolling Counter (하위 4bit) |
| 7 | `crc8` | uint8 | - | Byte0~6에 대한 CRC-8 |

**`0x200` — VEHICLE_STATUS (차량 → 조종기, 100 ms 주기)**

| Byte | 필드 | 설명 |
| --- | --- | --- |
| 0 | `state` | 시스템 상태 (RUN / E_BRAKE / LINK_LOST / FAULT) |
| 1 | `distance_cm` | 전방 거리 (255 = 측정 불가) |
| 2 | `pwm_left` | 좌측 모터 실제 듀티 (%) |
| 3 | `pwm_right` | 우측 모터 실제 듀티 (%) |
| 4 | `err_count` | 누적 CRC/타임아웃 오류 수 |
| 5 | `cpu_load` | CPU 사용률 (%) — 실측 증빙용 |
| 6 | `counter` | Rolling Counter |
| 7 | `crc8` | CRC-8 |

CAN은 ID가 낮을수록 우선순위가 높다. 제어 명령(0x100)에 상태보고(0x200)보다 낮은 ID를 할당한 것은 버스 경합 시 제어 프레임이 먼저 나가야 하기 때문이다.

> ⚠️ **I2C 솔더 브리지 확인:** UM1956에 따르면 A4/A5와 D4/D5의 I2C 배선은 SB16/SB18 설정에 따라 달라진다. 기본 상태에서는 PB6=D5(SCL), PB7=D4(SDA)로 알려져 있으나, LCD가 안 잡히면 이 브리지를 가장 먼저 의심할 것.
> 

### 4.2 Node 2 — NUCLEO-F446RE (차량)

| CAN1_RX / TX | PA11 / PA12 | CN10 | CAN1 (AF9) |  |
| Motor L ENA (PWM) | PA6 | D12 | TIM3_CH1 | 20 kHz |

> **PWM 20 kHz를 쓰는 이유:** 가청 주파수(20Hz~20kHz) 위로 올려 모터 코일 소음("삐----")을 제거하기 위함. L298N은 스위칭이 느려 40kHz 이상은 무리이므로 20kHz가 적정선.
