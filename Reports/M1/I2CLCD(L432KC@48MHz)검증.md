## M1 - ② 1602 I2C LCD 드라이버 (L432KC @ 48MHz) 검증
### 1. 드라이버 설계 및 테스트
PCF8574 I2C 백팩을 통해 HD44780 컨트롤러를 4비트 모드로 구동하는 드라이버 작성. M1은 베어메탈 개별 검증 단계이므로 전송은 Blocking(HAL_I2C_Master_Transmit)으로 구현하고 M3에서 DMA로 교체할 수 있도록 전송 호출을 `bus_tx()` 한 곳으로 격리함.

```
PCF8674 → HD44780 비트 매핑

P7 P6 P5 P4 | P3 P2 P1 P0
D7 D6 D5 D4 | BL E  RW RS 
```

#### 1-1. 드라이버 설계 결정 

| 항목 | 선택 | 이유 |
|-|-|-|
| nibble 전송 | 3 Bytes (RS/DATA, E=0 → E=1 → E=0) | 통용되는 2Bytes 방식은 RS와 E가 같은 바이트에서 동시에 상승해 HD44780의 주소 셋업 시간 t_AS(min 60ns)를 위반함. |
| us 지연 | DWT 사이클 카운터 | HAL_Delay()는 1ms 해상도라 HD44780 초기화의 ≥100us 대기를 표현할 수 없음. HAL_RCC_GetHCLKFreq()를 매 호출마다 읽으므로 M2에서 SYSCLK이 바뀌어도 재조정이 불필요하고 RTOS의 HAL_Delay() 금지 조항도 함께 회피함. |
| Busy Flag | 미사용 (RW=0 고정) | BF를 읽으려면 PCF8574를 입력으로 전환하고 다시 되돌려야해 왕복이 늘어남. 고정 지연이 더 싸다고 판단함. |
| 오류 처리 | err_count | 화면이 안나올 때 배선 문제인지 코드 문제인지 구분 가능하게 디스플레이에 표시. |
| 주소 결정 | 0x27 → 0x3F 자동 탐색 | 모듈을 사전에 알 수 없기 때문. |

#### 1-2. 검증 시나리오 (6단계)

| STEP | 내용 | 검출 대상 | 결과 | 비고 |
|-|-|-|-|-|
| 1 | I2C 버스 스캔 (0x08 - 0x77) | 배선, 솔더브리지, 주소 | 통과 | 0x27 발견 |
| 2 | 초기화 + 정적 2줄 표시 | 4bit 진입 시퀀스, Function Set | 통과 | - |
| 3 | 문자셋 0x20 - 0x7F 전수 | DDRAM 주소 매핑, 결점 픽셀 | 통과 | 32칸 전부 점등 |
| 4 | CGRAM 커스텀 글리프 + 진행 바 | CGRAM 쓰기, 애니메이션 | 통과 | - |
| 5 | 전송 시간 실측 (DWT) | 성능 근거 확보 | 통과 | 섹션 2 참고 |
| 6 | 대시보드 레이아웃 20프레임@100ms | 잔상, 깜빡임 | 통과 | 없음 |

### 2. 측정 결과
측정 조건: HCLK 48MHz, I2C1 100kHz (커널 클럭 HSI16), nibble 3bytes, Blocking, PCF8574@0x27

#### 2-1. 실측값과 예측 모델 대조

| 항목 | 예측 | 실측 | 오차 |
|-|-|-|-|
| 명령 1개 (SetCursor) | 770us | 826us | +7.3% |
| 문자 16개 | 12.32ms | 13.19ms | +7.1% |
| 1줄 (16칸 패딩) | 13.09ms | 14.02ms | +7.1% |
| 전체 2×16 프레임 | 26.18ms | 28.03ms | +7.1% |
| I2C 오류 | 0 | 0 | 0 |

네 항목의 오차가 모두 +7.1%로 동일하다는 것은 누락된 항목이 전송 건수에 비례하는 상수라는 뜻임. 역산하면 HAL 호출 1건 당 28us이고, 이는 START/STOP 컨디션과 HAL_I2C_Master_Transmit() 진입 오버헤드임. 이 항을 모델에 넣으면 오차가 사라짐.

#### 2-2. 전체 프레임(28.03ms) 분해 

| 구성 | 시간 | 비중 |
|-|-|-|
| 순수 I2C 버스 데이터 (2,448bit@100kHz) | 24.48ms | 87.3% |
| delay_us(50) × 34 (CPU spin) | 1.70ms | 6.1% |
| START/STOP + HAL 오버헤드 (68호출 × 28us) | 1.85ms | 6.6% |

병목의 87.3%가 데이터량이므로 최적화 방향은 데이터량을 줄여야 함.
최적화 선택지 비교 결과 UiTask 이용률도 낮고 규격도 준수하는 dirty-diff 방식을 채택함.

#### 2-3. RMS 예산
Node 1은 태스크가 4개이므로 Liu & Layland 한계 U = 4(2^(1/4) - 1) = 75.7%임. 
현재 Blocking + 전체 갱신 구조라면 우선순위 최하위인 UiTask가 단독으로 전체 예산의 37%를 점유하게 됨.

### 3. 향후 설계 결정

| # | 결정 | 근거 | 영향 |
|-|-|-|-|
| D1 | LCD는 5V인가 + 5V I2C 풀업. MCU 내부 풀업 OFF | ST 공식 답변 "모든 STM32 I2C 핀은 5V tolerant, VDD 선인가 조건". 3V3 구동은 HD44780 바이어스 부족으로 글자가 잘 안보임. | 회로도 `5V tolerant check needed` 주석 제거 |
| D2 | I2C1 커널 클럭을 HSI16으로 고정 | 기본값 PCLK1을 쓰면 M2에서 SYSCLK을 48MHz로 올릴 때 PCLK1이 함께 바뀌어 맞춘 TIMINGR이 무효가 됨. HSI16은 SYSCLK 변경과 무관하게 항상 16MHz임. | M2에서 CAN이 추가되었을 때 LCD가 깨지는 실패 경로를 사전 차단함. |
| D3 | UiTask는 dirty-diff 프레임 버퍼 + I2C DMA로 구현 | 현재 Blocking 및 전체 갱신은 28.1%로 RMS 예산의 37%를 점유함. dirty-diff로 6.6%까지, DMA로 버스 시간을 CPU 예산에서 분리해 1% 미만까지 줄이는 것이 목표임. | UiTask 역할을 dirty-diff 프레임 버퍼 + I2C DMA로 구체화. |
