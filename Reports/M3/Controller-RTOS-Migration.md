# M3-3 조종기 RTOS 이관 기록

작업일: 2026-11-09 (Asia/Seoul)

Node 1 L432KC의 20ms CAN 송신과 에코 검증을 FreeRTOS로 이관했다. 차량 Node 2는 M3-2에서 검증한 구성을 사용한다. **M3-3 정상 통신·RTOS 통합 시험은 사용자 보고 기준 PASS다.** 이번에 전달받은 양 노드 로그로 3,000회 왕복과 CAN 결과 출력 이후의 스택 여유·RTOS 상태를 확인했다.

## 구현 범위

| 태스크 | CMSIS 우선순위 | 스택 | 역할 |
|---|---:|---:|---|
| canTxTask | AboveNormal1 (33) | 1,024 B | CAN 시작/송신/정지, 20ms 주기, 종료 판정 |
| canRxTask | AboveNormal (32) | 1,024 B | ISR 큐에서 에코 수신, 순번·페이로드 검증 |
| ledTask | Normal (24) | 1,024 B | 녹색 LED 500ms 토글 |
| monitorTask | Low (8) | 2,048 B | UART 단일 출력, 시간·스택·힙·오류 진단 |

- STM32CubeL4 V1.18.2에 포함된 FreeRTOS V10.3.1 / CMSIS-RTOS2 / ARM_CM4F / heap_4를 사용한다. 힙은 15,360 B, RTOS SysTick은 1kHz다.
- HAL 1ms 시간 기준은 TIM6로 분리했다. PCLK1과 타이머 클록은 48MHz, PSC=47, ARR=999다. M2에서 사용한 LSE 기준 MSI 자동 보정을 스케줄러 시작 전 적용한다.
- CAN은 Normal 500kbps, Prescaler=6, BS1=13, BS2=2, SJW=2다. CubeMX의 `CAN1.NART=ENABLE`로 자동 재전송 설정을 보존한다.
- CAN TX/RX0/SCE IRQ 우선순위는 5, SysTick/PendSV와 TIM6는 15다. 커널 호출 가능 IRQ 경계도 5다.
- 커널 초기화 후 16슬롯 수신 큐를 생성하고 모든 태스크 생성 성공을 확인한다. CAN은 TX 태스크에서 시작한다. RX 태스크는 준비 플래그를 기다린 뒤 큐에서 대기한다.
- RX ISR은 한 번에 최대 3프레임을 읽고 헤더·도착 시각·8바이트 데이터를 큐에 복사한다. ISR 큐 삽입 timeout은 0이다. ISR 안에서 UART나 프로토콜 검증을 수행하지 않는다.
- 조종기는 ID `0x100`으로 순번 0…2999와 `55 AA 12 34` 꼬리를 보내고, ID `0x200`의 동일 데이터를 검증한다. 전송 등록과 실제 TX mailbox 완료를 별도 집계한다.
- 시작 후 2초 대기, 20tick 절대 주기, 마지막 송신 뒤 1초 대기다. 20tick 이상 늦으면 `slips`를 누적하고 다음 기준 시각을 재설정해 밀린 송신을 연속 실행하지 않는다. uint32 tick 래핑을 고려하며 실행 제한은 첫 송신 예정 시각부터 65초다.
- Bus-Off, 큐 손실/오류, 읽기 오류, 송신 등록 실패는 조기 종료 조건이다. 오래된 큐 항목은 타임아웃으로 처리한다. 수신 부족과 데이터 오류도 최종 PASS를 막는다.
- 종료할 때 CAN 알림/IRQ를 끄고 CAN을 정지하며 RX 태스크를 suspend한 뒤 결과를 고정한다. TX도 suspend 상태로 남겨 두 태스크의 스택 여유를 계속 읽는다.
- CAN PASS에는 수신/큐 삽입/처리/정상 검증/송신 시도/등록/완료 각각 3,000회, 빈 큐, 오류·주기 누락 0이 모두 필요하다. RTOS 오류와 스택 기준은 CAN PASS와 별도로 확인한다.
- 스택 overflow·malloc 실패·assert는 `m3.fatal_reason`을 남기고 정지한다. UART는 monitorTask만 사용한다.

이번 단계에서는 M1의 조이스틱/버튼/LCD 애플리케이션을 실행하지 않는다. 해당 기능의 태스크 통합은 후속 단계다. 기존 M2 모듈은 `M2_TEST_ENABLED=0`으로 보존하며 동시에 활성화하면 컴파일 오류가 발생한다.
